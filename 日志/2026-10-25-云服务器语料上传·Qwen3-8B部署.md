## 4. 云端 Git 将回到与 GitHub 相同的 commit

此前云端代码通过 SCP 手工同步，内容与本地一致但 HEAD 落后。本次收尾统一以
`origin/codex/agent-v2-reset` 的提交为基线：

1. 本地提交全部比较检索、holdout 和工程化收尾改动并推送。
2. 用 Git bundle 把同一提交传到云服务器，不依赖服务器访问 GitHub。
3. 云端 fast-forward/reset 到该 commit，只保留被忽略的 `workspace/` 与 `data/`。
4. 验收：本地与云端 `git rev-parse HEAD` 相同，云端 `git status --porcelain` 为空。

## 5. 比较题检索与 holdout 基线

比较题改为确定性分路检索：提取两个比较对象，分别检索并与组合查询做 RRF 融合；
比较题不再采用模型给出的过小 limit。方法列表按方法拆 claim，避免一题多论文事实
被合并成一个无法校验的 claim。

16 题验收连续两轮均为 `16/16`，两轮逐题的 route、refusal、claims、supported、
citations 完全相同；平均耗时分别为 15.29s / 13.52s，P95 为 37.04s / 30.39s。

比较题 holdout v1 已首次运行一次，结果 `10/10` 正常回答、0 错误，
38 条 claim 中 34 条 supported，自动 gate 通过（平均 23.414s，P95 30.840s）。
holdout 已标记 retired，`run_count=1`、`do_not_run_again=true`，不得再次运行。

## 发现的问题

### 1. 【最严重】入口无法稳定承载并行数据流

- 现象：24 年目录传完后，为 25 年再开一个并行 tar 流，新连接在 banner 阶段超时。
- 根因：`Collection@8.137.185.67` 到 253 的转发入口会拒绝并行数据通道。
- 证据：

```text
Connection timed out during banner exchange
Connection to 127.0.0.1 port 2253 timed out
tar.exe: Write error
```

### 2. 12 GB 显存无法直接加载 BF16 的 8B 模型

- 现象：模型权重为 16 GB，大于 RTX 3060 的 12,288 MiB 总显存。
- 根因：bf16/fp16 权重无法完整驻留显存。
- 证据：

```text
NVIDIA GeForce RTX 3060, 595.99.02, 12288 MiB
16G     /home/scu101/qwen-deploy/models/Qwen3-8B
```

因此改用 4-bit NF4 加载，并把上下文限制为 8,192 tokens。

### 3. GitHub 下载不可用，改用 ModelScope

- 现象：Ollama 安装脚本跳转到 GitHub 后超时，GitHub 主页也无法访问。
- 根因：服务器到 GitHub 的网络不通。
- 证据：

```text
curl: (28) Connection timed out after 30001 milliseconds
```

ModelScope 和 PyTorch CUDA wheel 源可正常访问，因此采用用户级 Python 部署。

### 4. 服务没有鉴权，也没有开机自启

- 现象：API 当前只绑定回环地址，未开放公网；服务器重启后需手动执行 `start.sh`。
- 根因：部署账号没有 sudo，当前先保证模型可运行，未配置反向代理、鉴权和系统服务。
- 证据：

```text
Uvicorn running on http://127.0.0.1:8000
```
